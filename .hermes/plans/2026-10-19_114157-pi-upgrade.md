# План обновления Pi: ядро, память и координация

**Статус:** план, не выполненное обновление. **Срез версий:** 19 октября 2026 года.
**База:** `main`, `3542c446603f985011d0911f7a8bfc5373ac452f`, текущая сборка Pi 1.0.4 build.6.
**Результат:** Pi 1.3.0 с сохранением наших функций памяти, работающими сабами, Goal X, Intercom и MCP/SSE в Code и Task.

## 1. Главное решение

Обновлять **плагины перед ядром**, одним последовательным кандидатом. Не устанавливать всё подряд и не менять внешние модели, данные и инструменты попутно.

**Очередь:** MCP → Subagents + Intercom → Memory и сохранение Session Search → Pi 1.3.0 и совместимость Goal X → общая приёмка → разрешённая установка себе.

MCP поставлен первым из-за исправления безопасности OAuth. Subagents обязательно обновляется до ядра: старая версия использует библиотеку `chord`, которую из нового Pi удалили. Изменения Memory под новый lifecycle готовятся до смены ядра. Goal X и Session Search уже последних версий: их не нужно переустанавливать ради номера, но их работу на новом ядре проверяем.

**Порядок загрузки не равен очереди обновления:** сохраняем **Subagents → Goal X → Intercom**, особенно Goal X перед Intercom. MCP Adapter остаётся единственным владельцем MCP; `-builtin:mcp` сохраняется.

### Что означает требование высокой уверенности

Конкретные несовместимости ниже установлены по исходникам и выпущенным пакетам. Это позволяет составить исполнимый план, но не даёт измеренной гарантии «99%». Работу именно нашей новой комбинации подтверждают короткие проверки на этапах 3–5. До них совместимость не объявляется доказанной. Неопределённость ограничена названными стыками, а не превращена в бесконечное исследование.

## 2. Что уже сделано и не делается заново

- В build.6 **Memory уже обновлён до 1.6.0**. Жёстко зашитая локальная Xenova-модель удалена. Оба механизма — Memory и Session Search — уже поддерживают внешние эмбеддинги: числовые представления текста для смыслового поиска.
- В принятой сборке обе памяти используют Polza / `qwen/qwen3-embedding-8b`, 1024 измерения; настройки у них отдельные. DeepSeek для извлечения фактов — отдельный маршрут, его не меняем.
- Привязку lessons к настоящему session ID уже исправляли мы. В upstream Memory 1.6.1 это **не исправлено**; публичный issue #35 остаётся открытым. Facts с provenance `consolidation` — другой тип записи, не та же ошибка.
- Сохранены различия Code/Task, исправления Windows, область видимости фактов и уроков, автоматический смысловой recall. Их нельзя потерять при замене patched-пакета штатным.
- В build.5 MCP Adapter 5.1.0 уже установлен в обоих профилях. Это сторонний `pi-mcp-adapter`, не собственный форк. Наше решение — выбрать его владельцем вместо встроенного MCP.

Node/npm, Serena backend, AST executable и optional MCP servers не обновляются попутно. Они не являются теми двумя текстовыми памятями, которые обсуждались выше.

Нужны отдельные bridge rebase и актуальные notices. Наши fixes удалённого onboarding checker и неподдержанного Python/Pyright implementations upstream не заменены.
- **AST CLI 0.45.3 → 0.51.0:** исправления записи файлов и новые grammar trust rules; новый wrapper всё ещё заявляет тестирование с 0.45.3. Не обещать совместимость новой пары без проверки, Windows staging остаётся нужен.
- **Context7 local 3.2.2 → 4.4.2:** stream/proxy/schema fixes, но наш template обращается к удалённому `https://mcp.context7.com/mcp`. Локальный npm update этот endpoint не обновляет. Его актуальный auth-контракт проверяется отдельно, без чтения ключей.
- **Brave 2.0.85 → 2.1.4:** schema/dependency fixes; HTTP hardening не выдавать за улучшение нашего stdio поиска.
- **Fetch 2025.4.7 → 2026.10.10:** полезная default-защита от private/loopback/cloud-metadata адресов; она намеренно меняет прежние intranet fetches. Не включать `--allow-private-ips` глобально попутно.

У Trace сохраняем русскую локализацию, Windows UTF-8 и профильные пути. На новом core custom-triggered interaction пока записывается с пустым prompt: это известное ограничение диагностики, не причина включать Trace глобально или блокировать обычную работу. Если нужна полнота custom trace, локально адаптировать обработчик, не выдавая служебное сообщение за пользовательское.

## 5. Этапы работ

### Этап 0. Подготовить один кандидат

1. Взять указанную базу и записанные exact targets. Использовать отдельную candidate branch/worktree и один выбранный каталог установки вне Git, существующие scripts, synthetic Code/Task.
2. Перед runtime-изменениями сохранить план/исходные документы в doc commit согласно BUILD. Фактический commit — только в разрешённом execution scope; сейчас он не выполняется.
3. Рабочие auth/settings/DB/sessions не использовать как fixtures. Не создавать VM, Sandbox, новый runner, backup-framework или дополнительную систему учёта.

**Готово, когда:** определены кандидат, каталог установки и точные версии; можно выполнять этап 1 без нового исследования состава.

### Этап 1. MCP Adapter 5.3.2

**Польза:** безопасность OAuth, устранение зависания startup в RPC, полные описания аргументов tools, сохранение direct-tool selection и исправления Windows.

1. Обновить pin и оба шаблона; сохранить `-builtin:mcp`, `scriptMode:false`, shared server configuration и credentials на прежних местах. Нашего patch Adapter нет: переносить его не нужно.
2. Учесть изменившиеся redirects и Windows secret-command shell только если соответствующие записи реально используются. Для старых OAuth credentials без issuer при необходимости выполнить безопасную повторную авторизацию затронутого сервера; не назначать issuer из недоверенной discovery, не экспортировать keyring. В 5.1 уже есть собственные issuer checks, поэтому версия SDK сама по себе не доказывает воспроизводимую атаку. Не делать массовую миграцию configs/auth.
3. Коротко проверить загрузку, discovery → describe → один безопасный вызов и сохранение direct-tool выбора. Реальный WVM на обоих transports оставить последним техническим шагом этапа 5.

**Готово, когда:** один MCP owner, нужные tools доступны, config/auth не заменены, переход к следующему этапу не зависит от неизвестного transport поведения.

### Этап 2. Subagents 0.79.1 + Intercom 0.17.1

**Польза:** совместимость без chord, надёжнее завершение/resume детей и освобождение слотов, supervisor/bg_wait, один parent wake, исправление Windows persistence Intercom.

1. Обновить два пакета, сохранив Goal X 0.32.3 и порядок Goal X перед Intercom.
2. Не переносить активные старые runs «на ходу» и не обещать новую resume-схему для детей, созданных старой версией. Fork теперь наследует родительский контекст/skills; это не информационная изоляция.
3. Одним локальным synthetic сценарием проверить child → вопрос supervisor → ответ → completion вместе с Intercom message: один wake, доступный итог, корректное завершение. Затем resume нового ребёнка создаёт новый output и не перезаписывает прежний. Resume сохранённой сессии не означает перенос владения активными runs в другой Pi process. В том же broker smoke проверить send/receipt, ask/reply и сохранение extension-state после restart.
4. Учесть lazy tools и новую форму `options`: не считать прежнее фиксированное число tools критерием исправности.

**Готово, когда:** новый child завершает полезный сценарий без chord; результат не теряется, оба расширения не запускают два parent turns на одно событие.

### Этап 3. Memory 1.6.1; Session Search 1.6.0 сохранить

**Польза обновления 1.6.1 ограничена:** диагностика AWS `credential_process`; поддержка Polza/внешних эмбеддингов появилась в 1.6.0 и уже принята нами. Обновляем до актуального patch-release вместе с необходимой адаптацией, а не выдаём этот маленький релиз за новую embedding-функцию.

1. В `patches/memory-windows-runtime/` взять чистый 1.6.1 и сделать один exact rebase. Сохранить Windows child CLI, ordered turns, profile settings, реальный session ID, aliases/scope/quotas, целые записи и automatic vector/hybrid recall, ephemeral context hook.
2. Сразу учесть `messageType: user/custom` нового Pi и явно закрепить lifecycle `pendingContextBlock`:
   - **В начале каждого нового запуска** очистить предыдущий block **до** поиска или раннего return; при смене сессии тоже сбрасывать.
   - Валидный непустой user prompt получает свежий recall. Пустой prompt или ошибка поиска не оставляют block прошлого запроса.
   - Custom не запускает новый поиск и не наследует прошлый block; не подставлять `undefined`, пустую строку или systemPrompt как запрос.
   - Внутри **одного user-run** block сохраняется между `context`/tool continuation вызовами; нельзя очищать его на каждом `context`.
   - Это осознанная политика сборки, не требование SDK: в custom Goal/Intercom продолжениях автоматического блока нет, при необходимости доступен явный `memory_search`. Отдельный early return без предварительного сброса недостаточен.
3. Не возвращать Xenova/ONNX/warm-up/timeout fixes: этот backend upstream уже удалил.
4. Проверить patch lifecycle на чистой копии: stock → apply → повторный apply → check → restore. Проверять изменённые поведенческие границы, не только маркеры.
5. Session Search не переустанавливать. Сохранить Code stock roots, Task profile roots, worker source routing, Windows containment и cleanup таймера. Его полная composed-проверка — этап 5.

**Данные не мигрируются:** provider, model ID, endpoint и dimensions не меняются. Ни массового backfill, ни `/session-reindex`. Одинаковая размерность не делает векторы разных моделей совместимыми; смена модели была бы отдельной задачей с отдельной согласованной SQLite backup API-копией. Откат пакета сам по себе данные не откатывает.

**Готово, когда:** patch 1.6.1 воспроизводим, наши функции сохранены, новый custom event безопасно обработан; изменение ядра больше не упирается в известный Memory mismatch.

### Этап 4. Pi 1.3.0 и стыковка Goal X

**Польза:** исправления streaming reasoning/tool JSON, Windows auth-lock, сохранение prompt additions, корректнее resume/tools; внутренние Pi-зависимости закреплены exact 1.3.0 вместо плавающих `^1.0.4`.

1. Обновить runtime pin и связанные fixture/version expectations. Использовать согласованный core/AI/TUI/agent-core набор; не менять Node/npm.
2. На одном synthetic Goal проверить обычный user turn → custom continuation/checkpoint → завершение. Отдельно различить настоящий пользовательский Esc/Stop и сбой provider. Goal settings и human focus сохраняются, `maxAutonomousRuns=0` не выставляется.
3. Если риск Goal подтвердился, минимально исправить различение user/custom как versioned patch с узкой проверкой. Не менять scheduler/политику автономности без необходимости. Если сценарий проходит — патч Goal не создавать.
4. Проверить host-first запуск Subagents, startup/busy wake, сохранение prompt additions после tool call, resume active tools и обработку `-p` length/exit 1. Для Polza — один offline stream contract с reasoning/tools/usage, `[DONE]` до delayed HTTP EOF и однократным RUB accounting. Latest `v0.2.1`/HEAD совпадают с нашим Git pin; адаптировать при необходимости locator старого SDK/chunk в тесте, не переписывать production provider по предположению.

**Готово, когда:** на новом core нет Memory hook errors, Goal не теряет продолжение и уважает Stop, дочерний результат не считается успешным при обрезке.

### Этап 5. Один общий проход и завершение

На окончательном кандидате, а не после каждого pin:

1. Загрузка Code/Task и core local-mock smoke; synthetic memory smoke в обоих профилях. Memory: русское перефразирование в automatic recall, project scope/aliases, целые записи, отсутствие injected memory в history/consolidation, ordered turns и lessons session ID. В существующий `tests/sdk/memory-smoke.mjs` добавить **одну последовательность**: user recall → tool continuation с тем же block → новый custom без block → пустой user/ошибка без старого block → новый валидный user со свежим recall → смена сессии со сбросом. Этот case пока отсутствует и подлежит реализации, новый runner не нужен. Session Search: worker завершился, свой synthetic session найден/прочитан, чужой путь отвергнут.
2. Коротко проверить Trace off → explicit opt-in → off на новом ядре; Background Tasks остаётся off. Не повторять все старые TUI/провайдерные матрицы.
3. Один repository verifier, один regression suite, safety scan и ручной просмотр итогового diff. Для изменённого patch — его собственные checks. Повторять только упавшую/исправленную границу, а не весь цикл с нуля.
4. **Последняя техническая проверка:** реальный безопасный WVM вызов через candidate Adapter отдельно по legacy SSE и streamable HTTP, с покрытием Code/Task: фактический transport, initialize/tools-list и read-only `settings_schema`. Для legacy SSE использовать Adapter `httpTransport:"sse"`, не неподдержанный импорт Pi-native `type:"sse"`. Автоматический fallback работает только на HTTP 404/405/406/415 и отключён при pinned `protocolVersion:"2026-07-28"`; auth/TLS/network error сам по себе SSE fallback не включает. Parent Hermes gateway и старый build.5 smoke этого не заменяют. Если нужный endpoint недоступен, записать конкретный NOT TESTED и не заявлять эту поддержку; не строить новый стенд.
5. После этого — только финальные docs/manifest согласование и разрешённые commit/release/установка себе. Новая существенная runtime-правка возвращает только её проверки и финальную transport-проверку затронутого кандидата.
6. Перед рабочей установкой один раз сохранить оба Code/Task профиля, launchers, exact runtime/package identities и patch states в private backup, общую memory DB — согласованной SQLite backup API-копией; не подменять их templates. Завершить активные runs; установить только выбранные exact версии, затем полностью перезапустить Pi и общий broker Intercom. Readback подтверждает фактические версии, фильтры и patch states обоих профилей. **Откат:** вернуть baseline executable/launchers и оба профиля; только изменённые данные восстанавливать из совместимой согласованной копии при остановленной БД, сохраняя candidate-only новые записи. Не считать Git revert откатом runtime/данных. Общий порядок — [state migration, «Откат»](../../docs/state-migration.md#откат); его старый статус Pi 0.99.1 исторический, baseline этого прохода — 1.0.4 build.6. Публикация и установка не выполняются автоматически из-за наличия плана.

**Готово, когда:** обе рабочие роли сохраняют прежние функции, новые версии проверены на согласованном составе, нет обязательного необъяснённого FAIL/NOT TESTED. Отчёт — изменения, результаты, ограничения, следующая допустимая операция; без новых кругов «проверки проверяющих».
