## Единственное breaking change ядра и почему состав не ломается

В 1.6.0 `Component.render()` возвращает `readonly string[]`, а `Container` кэширует склеенный массив и отдаёт тот же экземпляр, пока дети и ширина не изменились (причина — фикс saturating CPU при скролле, #9549). Ломает только код, который **мутирует** полученный массив (`super.render().push(...)`).

Проверка по составу: `super.render(` — **0** вхождений во всех 15 пакетах профилей (14 npm + git `pi-polza`, у него ноль импортов ядра); все 14 вызовов `render()` у TUI-компонентов (`pi-subagents`) только читают (`slice`, spread, `for..of`, `.length`, `[0]`). Пятнадцатый `render` в `pi-mcp-adapter` рендерит фоновую задачу и к TUI не относится. Задетыми не оказались ни `pi-subagents` (`fleet`, `fleet-viewport`, `fleet-status`, `fleet-transcript`, `render`), ни `pi-context-inspector`, ни остальные.

Почему массив не «падает» с ошибкой: он не замораживается, поэтому старая мутация портила бы кэш молча — статическая проверка здесь единственный дешёвый способ это поймать, живой TUI проверяет только визуально.

## Поведенческие сдвиги ядра, которые нас касаются слабо

- `find`: шаблоны путей теперь относительны к искомой папке (`src/*.ts` больше не находит `pkg/src/a.ts`, нужен `**/src/*.ts`). В наших доках и навыках шаблонов `find` со слэшем — 0.
- llama.cpp-расширение ядра по умолчанию переехало на порт 9931; в профилях оно не используется (Bonsai живёт отдельно и через это расширение не подключён).
- `pi.exec` отдаёт коды 128+signal вместо 0 при убийстве сигналом — более честное поведение, наших скриптов не касается.
- Исправлены: инструменты из `tool_search` больше не теряются на `resume`/`/reload` при `toolActivation: "auto"` (режим `pi-subagents`), вывод git/npm и служебные предупреждения больше не рисуются поверх TUI, RPC не вызывает `session_start` дважды, полный экран не жрёт ядро CPU на скролле, терминал корректно восстанавливается после выхода и `kill -TSTP`.

## Установка (Windows, эта машина)

`npm install -g` падает с `EBUSY` на `pi-tui\native\win32\win32-platform.node`, пока жив хоть один процесс ядра. Крестик на окне Herdr **не** останавливает агентов: панели живут в сервере, поэтому нужен `herdr server stop` и проверка «ноль процессов `pi-coding-agent`». Установка выполнена из чистой консоли, затем убран в корзину мёртвый staging-каталог прошлой неудачной попытки (`.pi-coding-agent-CiqA9OzT`), дерево `openai` проверено прямым импортом.
