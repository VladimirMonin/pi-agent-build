# План испытаний Pi 0.99.1 в изолированной лаборатории

**Статус:** план, не выполненная миграция. Рабочая сборка и `main` по-прежнему закреплены на `@earendil-works/pi-coding-agent@0.87.0`; опубликованный baseline — `pi-v0.87.0-build.2` (`1564e392b0088717814d83ea6cbf0ac119dc6885`). Целевая версия кандидата — **0.99.1**, но перед началом работ нужно повторно сверить опубликованные релизы и выбрать точную версию. Этот документ не меняет manifests, профили и установленный Pi.

**Цель:** выяснить, стоит ли выпускать следующую переносимую сборку на Pi 0.99.1, не повредив текущие Code/Task, память, авторизацию и рабочий CLI. Отдельно проверить, дают ли новые модели доступные владельцу провайдеры. Наличие модели в каталоге Pi не подтверждает её доступность или корректный ответ от Polza, OpenAI/Codex либо Anthropic.

Источники изменений: [v0.87.1](https://github.com/earendil-works/pi/releases/tag/v0.87.1), [v0.99.0](https://github.com/earendil-works/pi/releases/tag/v0.99.0), [v0.99.1](https://github.com/earendil-works/pi/releases/tag/v0.99.1), [MCP в Pi 0.99.1](https://github.com/earendil-works/pi/blob/v0.99.1/packages/coding-agent/docs/mcp.md). Не переносить выводы о поддержке модели или совместимости расширения на более позднюю версию без новых проверок.

## Границы и размещение

| Область | Рабочая установка | Лаборатория |
|---|---|---|
| Исходники сборки | `<REPO_ROOT>` / чистый `main` | `<LAB_WORKTREE>` / отдельная ветка `lab/pi-0.99.1` от опубликованного baseline |
| Исходники Polza | отдельный репозиторий; без изменений по умолчанию | не создавать форк плагина, пока не доказана конкретная несовместимость |
| Pi и npm | действующие глобальные executables | `<LAB_ROOT>/npm-prefix` и запуск **явным путём** к лабораторному Pi |
| Code / Task | действующие профили | `<LAB_ROOT>/pi-root/agent` и `<LAB_ROOT>/pi-root/task` |
| Сессии, трассы, логи, кеши | действующие пользовательские данные | приватные подкаталоги `<LAB_ROOT>`, вне Git |
| SQLite memory | действующая глобальная БД | отдельная пустая/синтетическая БД, изоляция которой доказана до запуска |

`<LAB_WORKTREE>` и `<LAB_ROOT>` — **разные каталоги**, оба вне репозитория `main`. Каталог ранее использовавшихся smoke-тестов не считать пустым и не очищать. Worktree изолирует только Git-файлы: это **не** песочница ОС; запускаемые расширения имеют права текущего пользователя. Вариант с отдельным пользователем ОС предпочтительнее, если проверка маршрутов записи либо общих ресурсов покажет недостаточность process-local изоляции.

**Инварианты:** не выполнять `pi update`, глобальный `npm install -g`, `setx`, установку launchers в пользовательский `bin`, миграцию живой БД или `git push` лабораторной ветки как побочный эффект испытаний. Не копировать в публичный Git `auth.json`, `models.json`/MCP с ключами, память, сессии, индексы и реальные логи. Записи `source=user` не менять без отдельного согласия владельца. Для оплачиваемых запросов к новым провайдерам получать явное разрешение на соответствующий тест; отсутствие доступа фиксировать как **NOT TESTED**, а не PASS.

## Этап 0. Baseline и перечень изменений

1. Сверить чистый `main`, `origin/main` и опубликованный тег; сохранить версии Node/npm/Pi, manifests, package sources и результаты текущих `verify`/safety checks. Данные проверки хранить приватно, не добавлять runtime-логи в Git.
2. Составить матрицу изменений от 0.87.0 до выбранной версии: модельный каталог и API/think controls, расширения, CLI, MCP, `--no-extensions`, SDK/RPC, настройки и миграции.
3. Отметить, какие возможности нужны сразу: новые модели, виртуальная маршрутизация, `codemode`; что уже покрывает `pi-mcp-adapter`; что должно остаться как есть. Отдельно выписать известные уязвимости npm-дерева для последующего аудита: смена версии Pi сама по себе не считается их исправлением.

**Выход:** baseline и таблица «новое → выгода → риск → тест». **Стоп:** не начинать установку, если исходный checkout или рабочие профили уже имеют неожиданные изменения; сначала разобраться, не стирая их.

## Этап 1. Подготовить изоляцию до установки

1. Создать worktree/ветку от baseline, приватный `<LAB_ROOT>` и тестовый cwd вне рабочего проекта. Проверить отсутствие ранее существующего содержимого целевых путей; не переиспользовать их через `--force`.
2. Определить allowlist переменных/путей для каждого запуска: `PI_CODING_AGENT_DIR`, отдельный npm prefix, home/config/cache, session directory, cwd, настройки внешних tools. Проверить launcher и дочерние процессы, которые могут игнорировать профиль; исключить наследование рабочих credential-переменных по умолчанию.
3. Особый gate для памяти: `PI_CODING_AGENT_DIR` **не** меняет автоматически стандартный путь `~/.pi/memory/memory.db`. Подготовить отдельный home **или** документированную project-local настройку `pi-memory.localPath` в тестовом cwd; проверить настройки и разрешение пути статически. Пока пакет не установлен в лаборатории, реальное открытие БД не подтверждено. Аналогично выявить общие session-search, MCP, trace, Goal-X и intercom state. Не направлять smoke в чужой проект с project-local настройками.
4. Проверить allowlist на безопасном подставном дочернем процессе, зафиксировать состояние глобального Pi/профилей/БД до установки. Одно лишь значение переменной окружения не является доказательством изоляции настоящего Pi: runtime-проверка после установки — отдельный обязательный gate на этапе 2.

**Выход:** предварительная карта путей и отсутствие глобальных записей в dry-run/подставном процессе. **Стоп:** любой неожиданный доступ на запись к рабочей установке. Никаких реальных credentials, личной БД и модельных вызовов до runtime gate.

## Этап 2. Сделать установщик и verifier пригодными для лаборатории

1. В **лабораторной ветке**, а не в рабочем `main`, обеспечить параметризованную установку Pi точной версии в отдельный npm prefix и вызов его бинарника явным путём. `install.ps1 -PiRoot` сам по себе недостаточен: текущий `-Apply` устанавливает npm, Pi и Code tools **глобально**. Аналогично проверить POSIX installer и оба verifier: сейчас они ориентированы на глобальный Pi и lock 0.87.0.
2. Предусмотреть dry-run, fail-closed preflight и проверку двух профилей до package writes; никаких тихих fallback на глобальный `pi`/`npm`, глобальную установку `uv tool` или перезапись пользовательских launchers. Внешние Code tools можно безопасно проверять или явно поставить отдельно; использование имеющихся глобальных бинарников не считать доказательством переносимости лабораторной установки.
3. После предварительного gate этапа 1 обновить **кандидатный** runtime lock на выбранную точную версию и относящиеся к ней installer/verifier/тесты. Источники 15/12 пакетов сохранять закреплёнными, пока отдельная совместимость не потребует контролируемого изменения. Применение patchers — только к лабораторным профилям.
4. Поставить оба лабораторных профиля; подтвердить фактический путь бинарника Pi, версии, package filters и порядок Goal-X → intercom. После установки, но **до** загрузки реальных данных/credential и модельных вызовов, провести runtime isolation gate на пустых синтетических данных: проверить реальный открытый memory.db и WAL/SHM, запись, сессии, MCP/trace и дочерние процессы, сравнить состояние рабочих путей до/после. Повторная установка не должна менять рабочий global npm prefix.

**Выход:** идемпотентные plan/apply/verify, доказанный runtime isolation gate и diff исходников без runtime-данных. **Стоп:** если какой-либо шаг требует менять global Pi, пишет в рабочее хранилище или маскирует сбой флагом `SkipPatchChecks`/`SkipExternalChecks` ради ложного PASS.

## Этап 3. Совместимость патчей и расширений

1. Проверить `pi-memory@1.5.0` на новом Pi без использования живой БД: `--check` version/hash-guard, синтетические регрессии scope/embedding/lesson budget/целых записей и фактическую инъекцию. Если upstream-пакет изменился, старый patch **не** применять к неизвестному bundle; сначала измерить upstream и пересмотреть patcher.
2. Проверить Trace, session-search, Serena, Codebase Memory, todo, Goal-X, intercom, subagents и Polza на обоих профилях; не сводить проверку к загрузке без ошибки — проверить конкретные команды/tools и границы событий в JSON/headless режиме.
3. Отдельно проверить ребёнка для консолидации памяти: `--no-extensions` в новом Pi отключает и built-in extensions; статический `polza-memory` из лабораторного `models.json` должен сделать реальный безопасный запрос без загрузки динамического провайдера. Секрет передавать только разрешённым приватным способом, не через аргумент или публичный лог.
4. На первом кандидате оставить `pi-mcp-adapter`: встроенный MCP замещается расширением, зарегистрировавшим `/mcp`, и не поддерживает legacy SSE. Проверить действующие MCP-серверы и WVM. Миграция на встроенный MCP — **отдельный эксперимент** после подтверждения streamable HTTP-эквивалента WVM и покрытия нужных функций адаптера; не запускать одновременно две конкурирующие конфигурации `/mcp`.

**Выход:** матрица Code/Task × plugin/patch с PASS/FAIL/NOT TESTED и адресными причинами. **Стоп:** потеря scope памяти, неизвестное состояние патча, ошибка ребёнка или неработающий обязательный MCP-маршрут.

## Этап 4. Реальные модели и исходящий запрос

1. Сверить каталог и параметры без сетевого вызова. В релизах заявлены GPT‑6 Sol/Luna и Claude Opus 5.5 (0.87.1), Claude Sonnet 5.5 (0.99.0), GPT‑6.1 Sol на OpenAI/Azure OpenAI Responses/OpenAI Codex (0.99.1). Проверить точные ID, провайдер, reasoning, контекст/лимиты и отображаемые возможности в **кандидатном** runtime.
2. Для Polza отдельно проверить, какие модели реально перечисляет и принимает сам Polza; обновление Pi не предоставляет автоматически GPT/Claude через Polza. Новый OpenAI/Anthropic маршрут проверять только если есть соответствующий доступ и отдельное разрешение на расход квоты. Не копировать рабочий `auth.json` в лабораторию и не утверждать, что подписка снимает лимиты.
3. Сделать минимум один живой запрос в Code и Task по текущему основному маршруту, плюс запрос к каждой **заявленной в выпуске** новой модели. Снять приватное подтверждение исходящего payload/response: корректный model ID, фактический провайдер, reasoning, вызов инструмента, ошибки/лимиты. Не публиковать payload с пользовательским контекстом.
4. На отдельной синтетической БД памяти проверить, что в **фактическом запросе к модели** присутствует полный `<memory>` без чужих scoped-записей и обрезанной последней строки. `source=user` в рабочем хранилище не трогать.

**Выход:** отдельная модельная матрица «каталог / auth / реальный ответ / tool call / лимиты». **Стоп:** нет проверенного ответа — не заявлять поддержку соответствующей модели как свойство новой сборки.

## Этап 5. Проверки платформ и release gate

1. Запустить unit/contract tests, оба repository/profile verifier, JSON/schema и синтаксические проверки, relative Markdown links, `git diff --check` и public safety scan. Затем повторить живые Code/Task smokes после финального изменения кандидата.
2. Windows проверять нативно. POSIX shell-тесты в Git Bash отмечать как POSIX-синтаксис на Windows, **не** как нативный Linux/macOS. При отсутствии нативной машины явно оставить платформу NOT TESTED и не расширять заявление о поддержке без проверки.
3. Провести ручной review каждого staged файла: ни абсолютных личных путей, ни ключей, ни БД/сессий/logs в Git. Разделить findings на дефекты новой версии, существовавшие дефекты сборки и непроверенные возможности. В release notes перечислить остаточные риски, включая аудит npm-зависимостей.
4. **GO:** оба профиля проходят обязательные gates, новые возможности подтверждены в пределах заявлений, рабочая установка неизменна. **NO-GO:** критичная регрессия памяти, Polza, обязательных MCP/субагентов или недоказанная изоляция. Если нет доступа к конкретной новой модели, можно продолжать исследование ядра, но не выпускать обещание её работоспособности.

## Этап 6. Публикация и откат (отдельное решение)

- После GO подготовить один или несколько смысловых commits на лабораторной ветке, проверить чистое дерево, синхронизировать с `origin/main` и получить отдельное решение о переносе изменений в `main`. Один лишь лабораторный PASS не разрешает автоматически обновлять рабочие профили.
- Обновить README/setup/manifests/patch docs по **фактическому** результату. На проверенном commit выпустить аннотированный тег `pi-v<версия Pi>-build.<номер>` и push только после отдельного разрешения владельца на выпуск. Тег 0.87.0 и прежний commit остаются неизменными.
- Перед последующим переключением рабочих Code/Task сделать приватные backups конфигов и данных с возможностью отката, проверить сохранность `source=user`, переключать обе установки контролируемо и повторить реальный smoke. Откат означает вернуть **исполняемый Pi, оба профиля и данные**, а не только сделать `git revert`. Резервные копии и новый runtime вне публичного Git.

## Что считается законченным сейчас

Публикация **этого плана** не выполняет этапы 0–6 и не доказывает совместимость 0.99.1. Следующий срез должен начинаться с инвентаризации и isolation gate; никакой установщик не запускать в режиме записи, пока gate не подтвердит отсутствие записей в рабочие пути.
