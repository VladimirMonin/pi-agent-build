# Обновления личной сборки — короткий план

## Правило владельца

Это личная сборка. Работаем короткими законченными обновлениями: **исследование → минимальные изменения → запуск и проверка → commit/push/release → установка себе → полный перезапуск**. Не ждём следующих upstream releases и не двигаем выбранные версии вслед за latest.

Без новых стендов, VM, isolation frameworks, широких аудитов, платных проверок по умолчанию и многоступенчатых approval loops. Один ответственный writer. Один read-only саб уточняет текущий план, не создаёт дополнительные этапы. Конкретный баг исправляем локально и повторяем только связанную проверку. Рабочие settings, auth, память и sessions не заменяем шаблонами. Goal X settings и human-owned focus не меняем.

## A — следующий релиз

Pi остаётся **1.0.4**. Обновляем только:

- `pi-subagents`: **0.76.0 → 0.76.1**;
- `pi-goal-x`: **0.31.9 → 0.32.3**;
- `pi-intercom`: **0.13.0 → 0.16.1**.

1. Сохраняем **Goal X перед Intercom**, изображения и все прочие версии/настройки. Порядок работы: Subagents → Goal X → Intercom.
2. Существующими средствами запускаем кандидат Code/Task в отдельном обычном каталоге с synthetic settings/state. Не создаём новый installer или test framework.
3. Короткая проверка: `tests/sdk/profile-loading.mjs <SDK_ROOT> <SYNTHETIC_PROFILE>` отдельно для Code/Task в private HOME; synthetic background completion разбудил parent обычным turn и сохранил prompt additions. Одним коротким совместным smoke проверяем старый synthetic goal с `nextAction`, его продолжение/завершение, обмен двух локальных test-сессий Intercom через Windows broker и idle wake. Сохранённый порядок Goal X → Intercom проверяем этим же headless сценарием; старую матрицу не повторяем. Fake transient recovery проверяем дополнительно только при конкретном дефекте. Публичный Subagents RPC/Polza contract по переданному исследованию не менялся: отдельный paid Polza smoke не требуется.
4. `scripts/verify.ps1 -RepositoryOnly`, `tests/scripts/run-tests.ps1`, safety scan и просмотр diff. Core-only smoke не повторяем: Pi не меняется. Если всё работает — один mini-release **`pi-v1.0.4-build.2`**, commit/push/tag/GitHub Release. Не расширяем support claims за пределы реально запущенного.
5. Ставим эти же три exact npm-spec себе штатным package lifecycle с явным `PI_CODING_AGENT_DIR` для Code/Task; не используем полный installer, `update --all`, замену configs или миграцию памяти/auth. До первой живой работы нового Goal X один раз сохраняем копию текущего `.pi/goals` вне Git: новый scheduler после сохранения теряет `nextAction`. Это одна копия данных, не разработка rollback-системы. Проверяем наличие custom `brokerCommand` только если он задан. Полностью перезапускаем Pi и проверяем обычный запуск. Готово.

[Release notes](../releases/pi-1.0.4-build.2.md). Исследования владельца служат входом, недостающие детали проверяются только при необходимости конкретного изменения.

## Следующие обновления — тот же алгоритм

Владелец досылает исследования. Они не расширяют этап A автоматически.

- **B — Serena 0.9.20 + Context Inspector 1.3.0:** следующий небольшой совместный релиз. Для Serena по исследованию владельца небольшой exact rebase: скрыть `serena_check_onboarding_performed` и `serena_find_implementations`, убрать упоминание `find_implementations` из `SERENA_FIRST_GUIDANCE`. Новый pristine для 0.9.20 и exact guidance patch; не расширять guard старых bytes. Serena Agent 1.7.0/Python/Pyright оставляем. Короткая приёмка: 20 stock → 18 visible tools, обе ложные capabilities отсутствуют, guidance их не предлагает, `serena_find_symbol` реально работает через Pyright. Не добавлять отдельный migration framework.
  - Context Inspector: чистый pin **1.1.1 → 1.3.0** в обоих профилях, без patch/config/data migration. По исследованию владельца обе версии уже относятся к одному текущему maintainer fork. Короткая приёмка `/context`: вкладки, resize/scroll/PageUp/PageDown, поиск и copy. Optional `e` проверить только если editor нужен; `$EDITOR` не менять попутно, отдельный патч для quoted Windows path с пробелами не добавлять.
- **C — Session Search 1.6.0:** исследование владельца принято как вход для небольшого нового exact patch, не механического переноса 1.4.3. Task сохраняет `<PROFILE>/session-search/{config.json,index}`, `<PROFILE>/sessions` и `<PROFILE>/sessions-archive`; Code сохраняет прежние stock config/index paths. Session/archive roots передавать штатно через `IndexOptions → workerData`, не патчить `dist/index-worker.js`. Учесть различие `PI_SESSION_DIR` плагина и `PI_CODING_AGENT_SESSION_DIR` Pi1.0.4; существующие явные overrides не терять. В `session_read` использовать фактические configured/profile roots и Windows-safe containment вместо `startsWith(root + "/")`. Сохранить cleanup проигравшего initial-sync timer. Короткая приёмка: worker стартует/закрывается, Task ищет и читает собственную synthetic session, Code читает свою, чужой путь отклоняется. Существующие config/index paths и Polza embedding config сохраняем; по исследованию форматы FTS/hybrid совместимы — forced `/session-reindex`, paid embeddings и смену `fusion` не добавляем. Если при реализации обнаружится конкретная несовместимость, исправляем только её.
- **D — Memory 1.6.0:** исследование владельца принято; небольшой rebase поверх upstream1.6, не перенос старого bundle целиком.
  - Не смешивать три отдельные роли: текущая консолидация памяти — `polza-memory/deepseek/deepseek-v4.1-flash` (в models.json объявлены text/image inputs); текущий локальный embedder фактов — **мультиязычный**, не мультимодальный, `Xenova/paraphrase-multilingual-MiniLM-L12-v2`,384d; Session Search отдельно использует Polza `qwen/qwen3-embedding-8b`,1024d. Consolidation model/provider и существующие model descriptors сохраняем, не заменяем новым embedding backend. Подтверждено read-only по установленным Code/Task settings/bundle/models; Session Search config подтверждён для Code.
  - Сохранить четыре runtime fixes: Windows child Pi через `process.execPath` + реальный CLI/prefix; упорядоченные `pendingTurns`; settings выбранного `PI_CODING_AGENT_DIR`; session ID через `sessionManager.getSessionId()`.
  - Оставить upstream `context-hook`, ephemeral injection, новые embedding providers/diagnostics, hybrid/RRF и backfill. Profile settings merge сохраняет `injectionMode`, `embedding` и наши `factProjectAliases`.
  - Перенести aliases, fact/lesson scope, whole-record fitting и section priority/quotas. Автоматический `<memory>` должен использовать vector recall через новый upstream embedder, а не только `memory_search`: **не ухудшать текущий русскоязычный automatic recall до FTS-only**. Удалённая upstream vector-ветка не означает, что наша функция больше не нужна.
  - Старый Xenova backend и его `withTimeout` cleanup удалить: соответствующего кода в 1.6 уже нет. Новый embedder выбрать отдельно: local Ollama/OpenAI-compatible либо согласованный другой provider; модель, downloads и платные calls не выбирать/запускать попутно.
  - Не смешивать embedding spaces. Одинаковые 384 dimensions не доказывают совместимость разных моделей: при смене модели с той же размерностью старые embeddings инвалидировать перед backfill; при иной размерности проверить штатный backfill. Facts/lessons/events сохраняем.
  - Перед первым живым включением нового embedder — одна согласованная SQLite-копия памяти вне Git (SQLite backup API учитывает WAL; не копировать один активный `memory.db` вслепую). После перезаписи vectors возврат package1.5 сам по себе не возвращает старое embedding space. Никакой новой backup/rollback-системы.
  - Короткая приёмка на synthetic DB: русское перефразирование попадает в automatic context-hook recall; чужие project facts/lessons не попадают; записи целые и corrections не вытесняются facts; memory block не пишется в history/consolidation. Одним consolidation fixture проверить порядок реплик, Windows executable/profile и реальный session ID. После этого обычный mini-release и установка себе; stock1.6 без наших функций не объявлять эквивалентом текущей сборки.
- **E — MCP Adapter 5.1.0:** выбрать одного MCP owner, проверить нужные серверы включая WVM. Не держать два владельца одних серверов.

Каждый этап — небольшой самостоятельный релиз и установка себе после запуска. Inspector входит только в B; Background Tasks остаётся выключенным и не обновляется без отдельного решения. Внешние инструменты и соседние настройки не трогаем. План зафиксирован; дальнейшие уточнения нужны только для конкретного обнаруженного дефекта или выбора embedding backend на этапе D.
