# Порядок загрузки `pi-goal-x` относительно `pi-intercom`

## Наблюдение

В headless-режиме (`pi -p`, `--mode json`, `--mode rpc`) создание цели через `create_goal` при загруженном `pi-intercom` печатает в stderr две ошибки:

```text
Extension error (<boundary>): turn_end could not resolve the persisted assistant entry ID
Extension error (.../pi-goal-x/extensions/goal.ts): This extension ctx is stale after session replacement or reload. ...
```

Ошибка **не фатальна**: цель создаётся, `status` = `active`, файл `active_goal_*.md` записан, exit code остаётся 0. В интерактивном TUI (проверено через pty) ошибка не воспроизводится.

## Что подтверждено экспериментально

Полная матрица: чистый Pi (`--no-extensions`) + один пакет сборки + `pi-goal-x`, пакет загружен **первым**, Goal-X **последним**. Проверялись обе величины: наличие ошибки в stderr и факт создания цели.

| Пакет перед `pi-goal-x` | ошибка | цель создана |
|---|---|---|
| `pi-ollama-cloud` | нет | да |
| `pi-trace-extension` | нет | да |
| `pi-context-inspector` | нет | да |
| `@juicesharp/rpiv-todo` | нет | да |
| `pi-polza` | нет | да |
| `pi-subagents` | нет | да |
| **`pi-intercom`** | **да** | **да** |
| `pi-background-tasks` | нет | да |
| `pi-session-search` | нет | да |
| `@samfp/pi-memory` | нет | да |
| `pi-mcp-adapter` | нет | да |
| `@nicknisi/pi-ast-grep` | нет | да |
| `@bacnh85/pi-serena` | нет | да |
| `pi-cbm` | нет | да |

Единственный пакет, при котором ошибка появляется, — `pi-intercom`. Цель при этом создаётся во всех случаях, включая `pi-intercom`.

Дополнительные контрольные точки:

| Условие | Результат |
|---|---|
| `pi-intercom` загружен **до** `pi-goal-x` | ошибка воспроизводится 10/10 |
| `pi-goal-x` загружен **до** `pi-intercom` | чисто 10/10, цель создаётся |
| `pi-goal-x` без `pi-intercom` | чисто |
| `pi-intercom` без `pi-goal-x` (с другими turn_end-расширениями) | чисто |
| `pi-intercom` с `{"enabled": false}` в `intercom/config.json` | чисто |
| другой turn_end-обработчик (trace, subagents, минимальный no-op) до `pi-goal-x` | чисто |
| интерактивный TUI при любом порядке | чисто |

Вывод: ошибку вызывает именно сочетание активного `pi-intercom`, загруженного раньше `pi-goal-x`, и только в headless-режиме. Это не несовместимость пакета: `pi-intercom` сам по себе и в правильном порядке работает чисто. Порядок обработчиков события равен порядку загрузки расширений, то есть порядку записей в `packages` в `settings.json`.

## Механизм

Первая ошибка приходит из ядра Pi: `_dispatchTurnEndBoundary` в `agent-session.js` не может сопоставить assistant-сообщение с записанной session entry (`_findPersistedMessageEntryId`) и прерывает диспетчеризацию boundary. Вторая — следствие: обработчик Goal-X затем обращается к уже инвалидированному `ctx`.

Точный внутренний шаг, из-за которого порядок двух расширений ломает сопоставление entry, не подтверждён пошаговой трассировкой; зафиксирован воспроизводимый корреляционный факт и надёжный обходной путь. Обе ошибки — следствие одной причины; вторая (про stale ctx) не означает реальной замены сессии.

## Решение в сборке

`pi-goal-x` размещён в `manifests/pi-packages.lock.json` и обоих `settings.template.json` **перед** `pi-intercom`. Это не патч: порядок закреплён декларативно, а `verify.sh` сверяет список пакетов шаблона с манифестом, включая порядок.

## Что проверить при обновлении

- Если `pi-intercom` или `pi-goal-x` изменят работу с `turn_end`/`ctx`, порядок может перестать быть обязательным — но и не станет вредным.
- Ошибка проявляется только в headless-режиме; интерактивная работа её не показывает, поэтому при автоматизированных прогонах (`pi -p`) её легко принять за сбой.
- Если после апгрейда любого из двух пакетов ошибка вернётся при правильном порядке — это признак изменения механизма, а не регрессии сборки.
