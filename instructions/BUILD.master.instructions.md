# BUILD — Master-инструкция переносимой сборки Pi Agent

## Назначение

Этот репозиторий — воспроизводимое описание персональной сборки Pi Agent. Он сохраняет состав, конфигурационные шаблоны, собственные навыки, локальные исправления, установочные сценарии и проверяемую документацию.

Это **не курс**, не снимок домашнего каталога и не архив пользовательской истории. Возможность дать ссылку другим людям является следствием воспроизводимости, а не изменяет назначение проекта.

## Целевой результат

Новая совместимая Windows-машина после выполнения документированной процедуры получает:

- зафиксированную версию Pi Agent;
- профили Code и Task с описанным различием;
- тот же набор Pi-пакетов и фильтров;
- `pi-polza` как нативный провайдер Polza AI;
- безопасные локальные конфиги, созданные из публичных шаблонов;
- воспроизводимые исправления сторонних пакетов;
- собственные Pi-навыки;
- проверку установки без публикации секретов и без обязательных платных вызовов моделей.

## Состав и границы

### Включается

- декларативный manifest с точными версиями;
- безопасные шаблоны `settings.json`, `models.json`, MCP и memory/session-search;
- воспроизводимые patch scripts с проверкой версии/сигнатуры;
- документация причины, применения, проверки и отката каждого исправления;
- launchers без абсолютного имени пользователя;
- собственные навыки после аудита на переносимость;
- installer, verifier и public safety scan;
- ссылки на исходники и лицензии сторонних компонентов.

### Никогда не включается

- `auth.json`, `.env`, токены, ключи и пароли;
- `memory.db`, `*.db-wal`, `*.db-shm`;
- сессии, traces, missions, логи живых запросов;
- `node_modules`, Python venv, модели, индексы и кеши;
- личный глобальный `AGENTS.md`;
- абсолютные пути конкретного пользователя или рабочей машины;
- приватные сведения, извлечённые из памяти или истории;
- рабочие конфиги, если в них когда-либо мог быть credential.

## Модель двух профилей

- **Code** — полный профиль: общие расширения плюс code intelligence (`ast-grep`, Serena, Codebase Memory и связанные env).
- **Task** — облегчённый профиль без дорогих code-intelligence tools.
- Для нового выпуска Trace остаётся установленным, но выключен по умолчанию в обоих canonical профилях; explicit opt-in/off имеет проверенные user/agent recipes. Не создавать третий режим. Фактическую готовность политики сверять с readiness board.
- Профили переключаются process-local переменной `PI_CODING_AGENT_DIR`; глобальный `setx` запрещён.
- Общие внешние источники (`~/.agents/skills`, корневой `AGENTS.md`, глобальный MCP) не считаются автоматически изолированными.
- Любое различие профилей должно быть выражено в шаблонах и описано, а не зависеть от ручной памяти владельца.

## Правило сторонних пакетов

1. Закрепляй точную версию в manifest.
2. Указывай официальный source/repository и лицензию.
3. Не вендорь package payload без необходимости и проверки лицензии.
4. Если пакет поставляет собственные skills, не копируй их: документируй и устанавливай пакет.
5. После обновления повторно проверяй filter entries и все локальные patches.
6. Не объявляй совместимость по номеру версии без запуска локальных контрактных проверок.

## Правило локальных исправлений

Каждый каталог `patches/<имя>/` должен содержать:

- `README.md`: дефект, причина, область, поддержанные версии, применение, проверка, откат;
- patcher или минимальный diff;
- pristine hash/signature либо надёжную структурную precondition;
- режим проверки без записи;
- fail-closed поведение на неизвестной версии/структуре;
- тест, который воспроизводит класс дефекта, а не только проверяет наличие marker;
- сведения о том, как определить, что upstream уже исправил проблему.

Обновление npm/Pi может перезаписать installed files. Поэтому update workflow всегда выполняет `check → apply if required → runtime verification`.

## Правило конфигурации и секретов

- Публичные файлы используют placeholders или ссылки на переменные окружения/secret command.
- Установщик создаёт локальные файлы, которые исключены `.gitignore`.
- Значение секрета не передаётся аргументом командной строки и не выводится в лог.
- Если исходный рабочий файл содержит секрет, его нельзя «скопировать и подчистить» в Git. Безопасный шаблон генерируется заново с allowlist полей.
- Повторный `/login` предпочтительнее переноса OAuth/session credentials.

## Правило документации

Документация описывает фактическую сборку:

- что установлено;
- зачем компонент нужен;
- что добавляет в Pi;
- где хранит конфиг и данные;
- какие секреты требуются;
- какие локальные исправления применены;
- как проверить и удалить;
- известные ограничения.

Не превращай описание в учебную программу и не добавляй искусственные «уровни» установки без запроса владельца.

## Workflow изменения состава сборки

1. Зафиксируй Git/working baseline, источник кандидата и scope разрешений.
2. Для upgrade прочитай [BUILD.LabUpgrade](BUILD.lab_upgrade.instructions.md); сверяй official stable target и однократно фиксируй exact version.
3. Подготовь и проверь исходные документы/контракт стенда; создай doc commit до runtime edits.
4. Проверь источник/лицензию и manifests; mutation только в разрешённом установочном каталоге/профилях. Обычное обновление не требует VM, native runner или отдельного isolation framework.
5. Обнови candidate manifest, templates и guarded patches; неизвестные source/bytes не принимаются по предположению.
6. Проверь actual Code/Task и changed seams, включая default-off/explicit opt-in Trace; source/mock/native claims раздельны.
7. Сопроводи код component docs, постоянными instructions и AGENTS каталогом в том же логическом срезе.
8. Выполни final relevant verification, links/schema/safety и ручной diff review на согласованном ref.
9. Создай смысловые commits; release/main/tag/working switch только в действующем scope владельца.
10. Тег — после обязательных accepted gates; repository publication не переключает живые profiles автоматически.

## Критерий готовности release-tag

Тег совместимости допустим, когда:

- manifests содержат точные версии и согласованы с installer;
- все JSON/YAML/PowerShell/Python/Node-файлы проходят синтаксические проверки;
- все относительные Markdown-ссылки разрешаются;
- safety scan не находит секреты, личные пути и запрещённые runtime-артефакты;
- patch checks дают ожидаемые состояния;
- verifier подтверждает структуру обоих профилей;
- README, component docs, AGENTS/instructions и upgrade/stand docs соответствуют manifest и реальному scope;
- два профиля и Trace defaults/opt-in проверены; actual runtime не заменён source-only checks, OS containment не заявлен без отдельно заказанной и проверенной границы;
- optional NOT TESTED отражены в ограничениях выпуска, без расширения support claims;
- рабочее дерево чистое;
- commit, на который ставится тег, уже создан и проверен.

Формат тега: `pi-v<версия Pi>-build.<номер>`.
