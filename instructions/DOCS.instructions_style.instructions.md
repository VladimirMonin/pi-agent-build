# DOCS — Создание и поддержка инструкций

## Обязательный формат

1. Имя файла: `PREFIX.topic.instructions.md` в корневом `instructions/`.
2. Первая строка — YAML с `applyTo`, `name`, `description`.
3. `name` имеет вид `PREFIX.Topic`; заголовок начинается с того же префикса.
4. Одна инструкция отвечает за одну устойчивую область: owner, contract или workflow.
5. `applyTo` покрывает релевантные пути; `**` применяется только к действительно сквозным правилам.
6. Пути, команды, версии и имена сверяются с текущим деревом и manifests.
7. На каждый файл есть рабочая Markdown-ссылка и условие чтения в `AGENTS.md`.

Для корневого `AGENTS.md` YAML не нужен: это краткий навигатор и полный каталог инструкций, а не ещё один подробный manual.

## Как писать description

`description` объясняет, **когда читать файл**. Включи типовые задачи, подсистему и затрагиваемые файлы.

Хорошо:

> Читай при изменении patcher, поддержанной версии пакета, процедур check/apply/restore и runtime-проверки.

Плохо:

> Важная информация о патчах.

## Когда обновлять или создавать

При изменении устойчивого workflow, owner, формата manifest/config, процедуры установки, patch contract, правила безопасности или release gate сначала найди существующую инструкцию.

- Подходящая область уже есть — обнови её в том же commit.
- Возник новый самостоятельный контракт — создай отдельную инструкцию и добавь её в каталог `AGENTS.md`.
- Изменился только частный текст документации — новая инструкция не нужна.
- Временный статус, история исследования и одноразовый incident принадлежат отчёту, changelog или issue, а не постоянной инструкции.

## AGENTS.md как живой каталог

Любая операция с инструкциями атомарна относительно каталога:

- добавление → новая строка в таблице `AGENTS.md`;
- переименование → обновление всех ссылок;
- разделение → ссылки на оба owner-файла и разные условия чтения;
- удаление → удаление ссылки и проверка, что правило действительно перенесено или устарело.

Если изменение кода или документации выявило устойчивое новое правило, агент обязан обновить соответствующую инструкцию в том же логическом срезе. Нельзя откладывать это как «документацию потом».

## Имена и объём

Рекомендуемые префиксы:

```text
BUILD  состав, установка, проверка, релиз
CONFIG конфигурационные шаблоны и профили
PATCH  общие правила локальных исправлений
SEC    публичная безопасность и credentials
DOCS   документация и commit-процесс
SKILL  собственные навыки Pi
```

Новый префикс оправдан новой ответственностью, а не желанием создать ещё один файл.

`AGENTS.md` остаётся существенно короче тематических инструкций. В нём допустим растущий каталог, но не копии их содержания.

## Проверка изменения

1. YAML начинается с первой строки и корректно разбирается.
2. `applyTo`, `name`, `description` соответствуют содержанию.
3. Нет дублирующего owner-файла.
4. Все пути и команды существуют либо явно обозначены как шаблон/план.
5. Новая/переименованная инструкция отражена в `AGENTS.md`.
6. Все относительные Markdown-ссылки разрешаются.
7. Нет личных данных, credentials или machine-specific путей.
8. Изменение входит в тот же commit, что и изменённый устойчивый workflow.
