# Общие правила Memory Ops

> АГЕНТ: прочитай этот файл целиком до первой операции в сессии.

## Философия

1. Память платит контекстом при каждой инъекции, поэтому длина важна.
2. Единица хранения — тема, а не отдельное предложение и не свалка фактов.
3. Перегруппировка меняет «тарелки», но не содержание: сверка N/N обязательна.
4. Любая мутация проходит этапы: предложение → dry-run на встроенном SQLite snapshot → явное согласие → проверенный внешний backup → apply → read-back.
5. Безопасный порядок: сначала сохранить замену, затем проверить, только потом удалить старое.
6. `source=user` — слова владельца. Удаление/rewrite/rename запрещены без отдельного owner override; после разрешённой правки provenance остаётся `user`.
7. Секреты и имя владельца не сохраняются и не копируются в артефакты.
8. Реальные логи находятся только в игнорируемом `runtime/` и не содержат текста записей.

## Подтверждённое поведение хранилища

Перед выводами сверяй установленную реализацию и схему — версии различаются.

- Факт адресуется по `key`; обычное обновление того же ключа — UPSERT.
- Урок адресуется по UUID; удаление часто мягкое (`is_deleted=1`).
- Активные уроки считаются только с `is_deleted=0`.
- Добавление урока может дедуплицироваться по текстовой близости, поэтому bulk script пишет транзакционно и сам проверяет вставку.
- Ручной API может принудительно маркировать факт как `source=user`; машинное слияние нельзя выдавать за слова владельца.
- `source` может включать `user`, `consolidation` и version-specific машинные значения. Неизвестный источник считай непроверенным, но не удаляй автоматически.

## Достижимость и бюджет

Каждая запись относится к одному из уровней:

1. **always-injected** — например, уроки с `project IS NULL`;
2. **domain-expanded** — соседи релевантного факта с ключом из 3+ сегментов;
3. **match-only** — leaf-ключи из 2 сегментов;
4. **unreachable** — не выбираются ни одним проверенным кейсом.

Порядок анализа: reachability → стоимость → ценность → стиль. Недостижимая запись не расходует текущий бюджет; её оптимизация не приоритетна.

### Co-expansion

При распространённой реализации ключ `a.b.c` входит в домен `a.b`; совпадение может подтянуть соседей. `a.b` — leaf и соседей не тянет. Это version-bound правило: подтвердить probe и установленным кодом, а не верить документу безоговорочно.

### Project slug

Уроки часто выбираются по `project=<slug cwd> OR project IS NULL`. Формат пути может менять slug. Не объявляй строку недостижимой по рассуждению: передай репрезентативные `{cwd,prompt}` в probe.

### Измерение

```bash
node scripts/inject-probe.mjs --db=<memory.db> --estimate
node scripts/inject-probe.mjs --db=<memory.db> --cases=<cases.json> --estimate
```

Probe читает стабильную byte-копию `db` + активный WAL во временный каталог, не открывая исходную SQLite. Простое ручное копирование только main-файла запрещено: оно теряет WAL pages. Probe не исполняет код plugin и выводит только структурные счётчики.

## Durable и volatile

- **Durable:** пути, gotchas, flags, пороги, стабильные предпочтения, способы восстановления.
- **Volatile:** «текущая версия», «задача открыта», «релиз уже вышел».

Snapshot не удаляется автоматически: обнови из source of truth или поставь дату. Наблюдение инструментом важнее памяти.

## Шкала ценности

Ценность — стоимость повторного открытия:

| Значок | Балл | Смысл |
|---|---:|---|
| 🔴 | 9–10 | без записи возможны часы отладки или блокировка |
| 🟠 | 8 | найденный экспериментом приём |
| 🟡 | 7 | важные пути, версии, параметры среды |
| 🟢 | ≤6 | полезно, но быстро восстанавливается |

Понижай оценку, если факт восстанавливается за 30 секунд или уже является source of truth в документации/валидаторе. Повышай, если ошибка тихая, частая и дорогая.

## Тематическая целостность

### «Одна тарелка»

Пометь 🌀, когда части отвечают на разные вопросы, имеют независимые решения или принадлежат разным подсистемам. Тест удаления: если убрать часть и остальное не потеряет смысл, темы могут быть разными.

### «Один сюжет»

Узкий кластер о едином процессе остаётся ✅, даже если отдельные предложения формально независимы. Этот тест важнее механического дробления.

### Размер

- ориентир: 200–500 символов на тему;
- потолок: 1000 символов;
- связный текст 500–1000 символов режется только при разных сюжетах, а не ради числа;
- глобальный бюджет важнее косметической атомарности.

## Диагнозы

| Значок | Диагноз | Доказательство |
|---|---|---|
| 💀 | ненужно | source of truth уже есть или факт мгновенно выводится |
| 🕰️ | устарело | путь/версия/инструмент проверены и не совпали |
| 🔁 | дубль | две записи несут одно знание, включая fact ↔ lesson |
| 🧬 | machine-generated | требует проверки, не означает автоматическое удаление |
| 🕳️ | недостижимо | probe не выбирает запись в репрезентативных кейсах |

Каждый диагноз содержит: что проверено, каким инструментом, что наблюдалось.

## Дубли между stores

Если fact и lesson повторяют одно правило, сравни реальную стоимость. Обычно селективный fact дешевле, но отрицательный lesson может быть намеренно always-on. Решение принимается по структурной оценке и содержательному review, а не по общему лозунгу.

## Формула короткой записи

```text
[Тема]: [суть/gotcha] — [решение/факт].
```

Удаляй связки, повторы и быстро восстанавливаемые детали. Сохраняй точные идентификаторы, пути, флаги, версии, числа и remedy. Контрольный вопрос: «что сломается, если убрать эту строку?»

## Owner override

Owner override состоит из двух независимых частей:

1. в разговоре владелец увидел точный `old → new`/delete list и явно согласился;
2. в CLI к `--apply` добавлен `--owner-override`.

Флаг без подтверждения не разрешает операцию. Dry-run показывает обезличенное количество owner records, но не пишет ничего; точные записи владелец проверяет в самом плане. После `BEGIN IMMEDIATE` owner guard вычисляется заново, поэтому смена provenance между dry-run и apply блокирует операцию как stale/owner conflict.

## Fail-closed plan и сохранность

- Merge-раздел, heading группы и обязательные поля совпадают точно; fenced/substring copies, неизвестные строки, дубликаты, missing rows и stale state отклоняют весь plan.
- `УДАЛИТЬ` всегда явный список и никогда не выводится автоматически из `ВОШЛО`.
- Каждая группа либо проходит, либо блокирует весь plan; partial apply нет.
- Protected identifiers, paths, flags, versions и числа должны находиться в source, результате и `ЧТО СОХРАНЕНО`. Coverage всегда 100% и не отключается параметром.
- Пустые keys/values/rules запрещены. Любое изменение fact value/key сбрасывает `embedding=NULL`.

## Секреты

Ищи marker-формы (`sk-`, `ghp_`, `api_key`, `password`, `secret`) без публикации значения. В report/log оставляй только публичный marker + `<REDACTED>`. После формирования артефакта отдельно проверь, что кусок секрета не попал в файл.

## Ошибка посередине

- До удаления старых записей состояние безопасно: не продолжай, повтори сохранение после диагностики.
- После частичной мутации остановись; прочитай точное состояние; сообщи, что создано и что осталось; восстанавливайся из backup только после согласования.
- Не сглаживай incident в итоговом отчёте.

## Локальные журналы

Форматы: [work log](../templates/work-log.example.md) и [defect log](../templates/defect-log.example.md). Журнал создаётся в `runtime/`, которое игнорируется Git. Чистый read-only run можно не логировать; реальную мутацию логируй сразу после read-back.
